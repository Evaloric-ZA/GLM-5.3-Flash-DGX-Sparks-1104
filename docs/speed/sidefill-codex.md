**Rank 1: probe the shared-expert branch.** If its GEMM currently runs on the main stream and can start from the same ready input as the routed experts, launch the *unchanged* GEMM on the side stream while the main stream runs routed experts. Join before the existing operation that combines their outputs. First confirm those dependencies and placement in the trace: the existing side helper may already cover part of this work.

The entire measured shared-expert stage is 0.89 s out of the 12.14 s main path. Even if all of it disappeared behind independent work at no cost, the bound is **7.3% less critical-path time, or 7.9% higher throughput**. That is an optimistic bound, not a prediction: only the portion between input readiness and the mandatory join can overlap, and concurrent kernels may compete for GPU and LPDDR bandwidth. The 6.79 s of side waits is not itself a speedup budget.

**Rank 2: inspect other independent branches, but do not build a cross-layer ring first.** Mixer and output projections, partial reductions, and glue are candidates only where a trace shows useful independent work between their input-ready point and their consumer. Moving a stage to another stream while the main stream immediately waits changes placement, not latency. Next-layer trellis preparation or prefetch may overlap, but activation-dependent work must wait for the preceding layer’s completed residual; prefetch can also contend for bandwidth. Keep kernels, operands, reduction order, and collective ordering unchanged.

**Rank 3: defer the expert row split.** It changes execution and potentially TP exchange or reduction order, making both the bitwise contract and a days-scale implementation harder. A ring cannot bypass the layer-to-layer residual dependency; it helps only for work whose result is consumed later and whose operands remain valid.

**Cheapest decisive probe:** use existing stage traces and NVTX ranges to map, for shared expert and each plausible branch, input readiness, first consumer, and existing event waits. Reject any branch with no independent main-stream interval. Then use a throwaway benchmark that replays the *same kernels and operands* sequentially and concurrently on two streams, with CUDA-event timing, including the join. Measure each alone and the combined makespan, using thick, interleaved repetitions. This tests dependency opportunity separately from resource contention without changing the engine. NVTX host ranges alone do not establish GPU overlap when CUPTI activity is broken; use the benchmark’s device timings, and try ncu only if needed to explain contention. A successful microbenchmark still needs an engine scheduling experiment and the eight-prompt `token_sha` gate before acceptance.

**Memory:** one 4,096 × 4,096 hidden-state slab is **32 MiB at 16 bits**, or **64 MiB at 32 bits**, per rank. A two- to four-slot ring is therefore 64–128 MiB at 16 bits or 128–256 MiB at 32 bits, excluding metadata and any additional or wider intermediates. Use one ready event and one consumed/reusable event per slot, recorded on each reuse; the main stream must wait before overwriting a live slot. The actual worst case requires the retained tensors’ widths, dtypes, and count. Against the stated ~20 GiB headroom and 8 GiB reserve, ~12 GiB remains for **both** staging and KV growth; verify projected KV growth before allocating it.

**Kill criteria:** stop this line if no sizable branch has a real independent interval, or if interleaved concurrent replay shows no repeatable joined-makespan reduction after accounting for run-to-run variation. Also stop a candidate if preserving the existing math and collective order prevents overlap. If the best repeatable upper bound is only around 2% end-to-end, favor the null result unless the scheduling change is demonstrably small.
